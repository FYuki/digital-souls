# 音声品質改善 共通実行指示書（#350・#423・#424）

## 状態と目的

2026-09-19のgrill-meで合意した要件に、同日のユーザー指示による受入範囲の変更を反映した。
欠測ゼロや厳密な率を保証する追加実装を今回の必須条件から外し、実利用上の品質担保へ絞る。
過去の失敗・欠測は再判定せず、以下の必須条件と追加保証を区別する。
文書の当初基点はmain e51bce16f83c156ffb53db0c3ded67c40cde5001。実行時は版と有効設定を固定する。

## 今回の必須確認（2026-09-19変更）

1. 初回起動の安定化、準備失敗の理由表示、手動再試行による復帰。
2. 実マイクでの複数往復。文中分割、音切れ、読み、声質、応答待ちを実用上確認する。
3. 準備中取消、割り込み、通信断、TTS失敗後の停止と後続会話への復帰。
4. 履歴・privacy・更新／切り戻しのデータ保全と互換性。
5. 変更に関連するテスト・CIと重要レビュー指摘への対応。

実マイクと人の聴感は自動試験で代替しない。ユーザー協力が必要な操作・所要時間・確認点は
[実用受入の手順](validation/voice-practical-acceptance-20260919.md)へまとめる。
再現した実会話障害やデータ欠損は引き続き原因を調べて修正する。
未変更機能の全面再試験を新たな必須条件にせず、変更の影響に応じた確認を行う。

### 追加保証へ移す項目

- VAD境界の欠測10件をすべて解消するための追加計測実装。
- 相槌・割り込み各100件以上による厳密な誤判定率の保証。
- 今回変更していない機能の全面再試験、計測専用コードの網羅的な高機能化。

これらは今回の完了を妨げる必須条件にしない。元Issueの将来の品質基準を満たしたとは主張しない。
休止の誤分割0/100・STT入力PCM照合100/100は既存の版・条件付き証拠として維持し、
境界時刻10件は未確認のまま残す。正式reportのFAILをPASSへ書き換えない。
空状態の速度目標は維持する。速度へ影響する変更は再計測するが、あらゆる変更で
一律に正式100件を繰り返さない。再計測の範囲と、速度へ影響しない判断の根拠を記録する。

既存LiveKitと自前音声制御の応答開始速度・通常会話の安定性を改善する。
3件を一つの計画として調査・計測し、修正は原因別PR、受入はIssue別に管理する。
全体計画は[#422](https://github.com/FYuki/digital-souls/issues/422)。

## 音声会話の開始準備

- 開始操作後に必要な準備を行い、「準備中」を表示する。準備完了後に発話受付を始める。
- 準備全体には固定の時間上限を設けない。60秒等の経過時間だけで失敗にしない。
- 各処理・サービスのタイムアウトとエラーは検出する。既存の要求・worker・入力ACK等の期限まで無効化する決定ではない。
- 準備失敗時は、失敗した処理と理由を表示する。Session開始準備全体を自動再試行せず、ユーザー操作で再試行する。
- 準備時間は開始操作から発話受付可能になるまで別途計測する。準備完了、初回応答、継続応答を混同しない。
- 開始準備の再試行方針を、既存の通信再接続や共有サービス内部の回復方式の変更へ広げない。

判断の根拠・優先関係は[開始準備ADR](decisions/voice-session-preparation-2026-09.md)、
用語は[用語集](glossary.md)を参照する。

## 評価の順序と条件

### 第1段階：空状態での速度受入

- 各試行は会話履歴が空、記憶参照なしで開始する。専用dev/testのdata rootを使う。
- 準備完了後の通常音声応答を、事前登録した100独立試行で測定する。
- 受入条件は利用者の発話終了から端末の実再生開始までのp95が2,000ms以下。
  BEの発話確定、first token、音声生成完了やtrack受信へ測定境界を置き換えない。
- 実施する計測では全予定試行を保持し、成功数・失敗・欠測・coverage・p50/p95を報告する。
  有効値だけのp95と全試行の成立状況を分け、失敗・欠測を除外して達成扱いにしない。
  #150の通常応答100試行の処理失敗0件等の既存条件も維持する。
- 準備失敗は応答時間へ架空の値を入れず、準備の失敗と応答未実施として残す。
  長い準備を隠した総合的な高速化の主張や、準備済み試行だけへの事後差し替えをしない。
- 既存手順のwarm-upが必要なら回数・内容・除外規則を事前固定し、準備の記録と対応付ける。
  未達後にwarm-upや除外条件を変えて同じcohortの合格にしない。

この受入を達成してから第2段階へ進む。未達は未達として記録し、閾値を事後緩和しない。
空状態は会話データ・記憶参照の条件であり、モデル未ロードの状態と同義ではない。

### 第2段階：記憶参照のみの追加計測

- 各試行は引き続き会話履歴を空から開始し、検索対象に固定したテスト用記憶だけを追加する。
- 第1段階と入力・モデル・採用音声・設定・計測境界を揃え、記憶の検索・参照による差を計測する。
  記憶集合・件数・検索設定・版を固定し、実際に検索・参照したことと、未参照・失敗・欠測を区別する。
- p50/p95、空状態との差、失敗・欠測と原因を報告する。記憶参照を省略した高速値を参照ありの値にしない。
- **計測のみであり、記憶参照の結果・速度は今回の受入条件に含めない。**
  2,000msの合格閾値、#358の回帰許容式、記憶参照の合格まで修正を続ける条件をこの段階へ適用しない。
  計測作業と結果・制約の記録は行うが、その数値を理由に3件の受入・完了を保留しない。
- 記憶形成（抽出・保存等のバックグラウンド処理）の影響調査と、長い会話履歴の影響調査は範囲外。
  両段階の専用試験では形成負荷を混ぜない条件を記録する。共有サービスやdogfoodの設定を変更して実現しない。

この限定比較から、記憶形成や長い履歴を含む通常利用全体の性能を保証しない。
既存のprivacy、所有境界、履歴保持の機能回帰条件を削除する決定ではない。

## 共通計測と今回の適用範囲

実行前にコードcommit、起動image、有効Profile・設定、STT/LLM/TTSのモデルrevision、
音声・処理設定、計測コード、fixture・hash、データ状態、負荷・共有資源を固定する。
採用音声はIrodori / miori-b3-4221 / B-3 Caption / seed 4221 / 40 steps / speed 1.02を維持する。

STT、推論準備・queue・モデル読み込み・最初の本文、先頭区間TTS、配信・実再生待ちを切り分ける。
段階別p95を足し合わせず、異なるhostのmonotonic時計を直接減算しない。
既存の固定WAV実接続と、人の実マイク・聴感受入を区別する。

| 項目 | 今回の必須と追加保証の境界 |
|---|---|
| 空状態の速度 | 第1段階のp95 2,000ms以下を維持。既存100件の証跡を条件付きで保持し、速度へ影響する変更は必要な再計測を行う |
| 再接続 | 停止・再接続・後続会話の復帰を確認する。既存100件の成功率・p95・sample/gapの証跡は保持する |
| 相槌・割り込み | 実用上の旧応答停止・後続会話への復帰を必須とする。各100件の厳密な率保証は追加保証 |
| BE移設後の品質 | 文中分割や音切れ等の実会話障害を調べて修正する。欠測ゼロのための計測実装は追加保証 |
| Irodoriの品質 | 採用音声の読み・区間間の途切れ・声質・応答待ちを人が確認する。取消・失敗後の復帰も確認する |
| 履歴・privacy・互換性 | 変更に関連するデータ保全、更新／切り戻しを確認する。未変更機能の全面再試験は追加保証 |

第2段階の固定記憶参照は計測のみであり、速度閾値を今回の合否へ加えない。
記憶形成・長履歴の影響調査は範囲外。既存のprivacy・所有境界・履歴保持は維持する。
元#150/#358の厳密な品質基準と過去の未達を、今回すべて解消したとは扱わない。
#350の過去の個人利用上の許容は記録に残し、#3の設計開始を停止する新しい依存は作らない。

## PRの分割と証跡の対応

| PR | 内容 | 含めないもの |
|---|---|---|
| 計測基盤の修正PR（必要時、先行） | 欠測・時計・集計等の不具合修正と検証。改善前後を比較できる状態にする | 製品の安定性・速度改善を混在させない |
| 製品修正PR（原因別） | 安定性・速度・開始準備の修正、その修正に必要なテストと実接続確認 | 横断的な正式100試行・正式受入記録の一括追加 |
| 測定・受入記録PR | 正式100試行、改善前後比較、第2段階の追加計測、Issue別判定と残課題の記録 | 製品コードの安定性修正を混ぜない |

改善前の版・有効設定・条件を修正前に固定し、改善後も対応付ける。
同じ計測条件で比較できるよう計測基盤の版も固定する。先行計測や原因切り分けの小規模診断を禁止するものではない。
修正PRにも必要な検証を含め、正式計測PRを理由に未検証の修正を統合しない。
測定で新たな不具合が見つかったら別の修正PRへ戻し、変更後の版を明記して再測定する。
測定PRを1件にするか段階別にするかは実行側へ委ねる。

専用worktreeを使い、作業PR→対応Epic→mainの運用に従う。
Epicへの統合は対象headのCI成功後、main向けはCodeRabbit差分レビューと必要修正を行う。
mainへのマージはユーザーが行う。文書更新、CI、マージを実性能受入の代用にしない。

## 制約・対象外と実行側への委任

- dogfoodの実会話データを試験へ流用しない。既存のデータ・音声資産・原証跡を保持する。
- 共有サービスの停止・再起動・設定変更、配備は今回の文書更新に含まない。
- Coreの大規模再設計、Pydantic AI導入、LiveKit Agentsへの置換を品質改善PRへ混ぜない。
- モデル・prompt・声を同時刷新しない。採用モデル・精度・声の変更は既存の別途判断の境界を維持する。
- compile無効を既定とする既存方針を維持し、有効化自体を完了条件にしない。
- 記憶品質改善・形成負荷調査・長履歴負荷調査、新しい評価基盤の新設は要求しない。
- 準備する処理の具体的な接続、画面上の配置、試験データの具体的内容と件数、
  診断の順序・計測の実装は、上記の要件・既存契約を変えない範囲で実行側へ委ねる。
- 原因・再現性・実測値は固定版の証跡に従う。過去値を未測定の版へ無条件に適用しない。
