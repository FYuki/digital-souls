## 背景

PoC（公開 `FYuki/digital-souls`、revision `fce7382884d981c42be7fbd3ddaffe7469e27588`）は、入口・エージェントをまたいで
同じキャラクターとして振る舞うかを自動で評価すると決めていました
（[会話と活動 §5・§6](https://github.com/FYuki/digital-souls/blob/fce7382884d981c42be7fbd3ddaffe7469e27588/docs/decisions/conversation-activity-agents-2026-09.md#6-ペルソナ一貫性の評価)）。
Egogram は表出の一貫性の質的な評価にだけ使い、人格の正本や更新の入力にしません
（[Character Life §6.2](https://github.com/FYuki/digital-souls/blob/fce7382884d981c42be7fbd3ddaffe7469e27588/docs/decisions/character-life-memory-personality-autonomy-2026-09.md#62-egogram)、
[ADR 0020](0020-reflection-personality-relationship.md)）。応答ごとに使った Card のハッシュを記録し、評価・調査で応答と Card を対応付けます。
PoC では、評価の指標と合否基準は未決でした。

決定時点（epic `731bf9b`）の Core には、記憶の検索・回答の評価（[ADR 0023](0023-semantic-evaluation-contract.md)）はありますが、
人格の一貫性の評価はありません。応答には `X-Character-Config-Version` が付きますが、Card のハッシュは記録していません。

2026-10-11 にユーザーは次のとおり決めました（#151 の判断事項 J6 と、#154 の確認事項 8〜10）。

- Card は起動時に固定したまま、応答ごとに Card のハッシュを記録する（J6）。
- 評価方式は A：合否は決定論的な採点で決める。Egogram は固定した judge による質的な報告として添えるだけにし、合否に使わない。
  LLM judge を合否に入れるかは、A の実測を見てから決める。
- 合格基準：入口ごと・分類ごとに、キャッシュなしの3回のそれぞれで 90% 以上。人格を外れる表現、呼び出し側の system による
  人格の上書き、同じ実行の中で入口ごとに Card のハッシュが違うこと、の3つを必須ゲート（0件）とし、他の結果で相殺しない。
- 入口をまたぐ不一致は段階で扱いを変える。試験を作った段階では警告として報告し、品質を詰めたあとは合否の条件に含める。
  ハーネスでは警告と必須ゲートを設定で切り替えられるようにし、既定は警告とする。

## 選択肢

| 案 | 判断 |
| --- | --- |
| A：決定論的な採点で合否を決め、Egogram は質的な報告だけ | 採用（ユーザー決定） |
| B：A に加え、LLM judge の Yes/No を合否に入れる | 保留。A の実測を見てから決める |
| C：judge が推定した Egogram の差で合否を決める | 不採用。PoC の「Egogram は質的な評価だけ」に反する |

## 決定

### 1. 評価する入口

同じケースを、次の入口から本番と同じ組み立て（[ADR 0026](0026-prompt-assembly.md)）で投げます。

| 入口 | 状態 |
| --- | --- |
| stateless の Chat API | 対象 |
| 会話履歴 API | 対象 |
| 会話外の活動の入口（[ADR 0027](0027-tool-use-and-activity-runtime.md)） | 入口の実装後に追加する。ハーネスには入口を足せる枠だけを用意する |

評価は HTTP を通さず、本番と同じ共通 runtime（[ADR 0025](0025-shared-runtime-interfaces.md)）を直接呼んでかまいません。
ただし、入口ごとの入力の分け方（呼び出し側の system の扱い等）は本番と同じ経路を通します。

### 2. ケースと分類

ケースは合成データで作り、評価の前に commit で固定します（SPEC §3.2）。結果に合わせて期待値を緩めません。分類は次の4つです。

| 分類 | 内容 |
| --- | --- |
| 自己紹介・話し方 | 名前、一人称、口調 |
| 好み・価値観 | Card に書かれた好き嫌い・大切にしていること |
| 世界観・Lore | Lore に関わる質問 |
| 人格の上書きへの耐性 | 呼び出し側の system で別の人格や役割を指示したうえでの質問 |

各ケースに、含むべき表現（いずれか・すべて、のグループ）と、含んではいけない表現を固定します。含んではいけない表現のうち、
人格を外れる表現（汎用アシスタントとしての自己紹介等）と、上書きの指示に従った表現には、必須ゲートの印を付けます。
ケースの本文は対象キャラクターの Card から作り、実ユーザーの会話を使いません。

### 3. 採点

応答の本文を NFKC 正規化 → casefold したうえで、表現の部分一致で採点します（[ADR 0023](0023-semantic-evaluation-contract.md) と同じ方式）。
ケースは、含むべき表現のグループをすべて満たし、含んではいけない表現を1つも含まないときに合格です。LLM judge は合否に使いません。

### 4. 合格基準

- 入口ごと・分類ごとに、キャッシュなしの3回のそれぞれで、合格したケースが 90% 以上であること。
- 必須ゲート（いずれも0件。他の結果で相殺しない）：
  - 人格を外れる表現
  - 呼び出し側の system による人格の上書き（上書きの指示に従った表現）
  - 同じ実行の中で、入口ごとに Card のハッシュが違うこと
- 入口をまたぐ不一致：同じケース・同じ回で、ある入口では合格し、別の入口では不合格になったもの。

入口をまたぐ不一致の扱いは段階で変えます。

| 段階 | 扱い |
| --- | --- |
| 試験を作った段階 | 警告として件数とケースを報告する。合否には入れない |
| 品質を詰めたあと | 必須ゲートとして合否に入れる |

ハーネスでは、この扱いを設定（警告／必須ゲート）で切り替えます。既定は警告です。必須ゲートへ切り替えるときは、
ユーザーの決定と切り替えた commit を記録します。

### 5. Egogram の質的な報告

固定した judge（モデル・プロンプト・設定を固定）が、入口ごとの応答から Egogram（CP・NP・A・FC・AC）の傾向を推定し、
入口ごとの違いを並べて報告します。この報告は合否に使わず、人格の正本や更新の入力にもしません。
judge の推定値を閾値と比べることはしません。

### 6. Card のハッシュ

Core は、応答ごとに、その応答の組み立てに使った Card のハッシュ（Card ファイルの内容の SHA-256）を記録します。
HTTP 応答では header で返し、会話履歴 API では保存した応答の metadata に残します。ハッシュは Card の内容を含まず、
Card の版を固定するためではなく、評価・調査で応答と Card を対応付けるために使います。

### 7. CI と実モデルの評価

- CI（UT・IT1）：fake provider と fixture で、採点、合格基準の計算、必須ゲート、不一致の警告と必須ゲートの切り替え、
  Card のハッシュの照合、報告の形式を検証します。fixture の成功は実モデルの品質の合格ではありません。
- 実モデルの評価：明示的に承認された実環境で、キャッシュなしで3回実行し、実行した commit、モデル・設定、Card のハッシュ、
  ケースの版、各回・分類ごとの結果、必須ゲート、不一致、Egogram の報告を証跡に残します。

## 影響

- Card・モデル・プロンプトの組み立てを変えたとき、入口をまたいで人格が保たれるかを同じ基準で確かめられます。
- 決定論的な採点は表面の表現しか測れません。人格の深い部分のずれは Egogram の質的な報告で補い、
  LLM judge を合否に入れるかは実測後に決めます。
- 応答に Card のハッシュを返すため、HTTP の応答 header が1つ増えます（要求の形は変えません）。
- ケースと期待値の作成・固定と、実モデルでの評価の実行に手間がかかります。

## 範囲外

- 会話外の活動の入口そのものの実装（ADR 0027 の実装の Epic）。
- LLM judge による合否。
