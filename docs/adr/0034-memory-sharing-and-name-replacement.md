# ADR 0034: 記憶の共有範囲と保存時の個人名の置き換え

## 背景

現在の長期記憶の正本・検索・参照は Binding（subject・client・audience・character）の完全一致を
前提としています。同じキャラクターでも、他の利用者から得た知識を参照できません。
ユーザーは #77 で、同じキャラクターが知っている長期記憶の条件付き共有と、会話履歴の非共有を
指定しました。2026-10-13 には、個人名を保存時に置き換え、管理者向けと配信向けで参照を制限する
方針、照合と訂正の適用範囲、#127 内での実装を指定しました。

本 ADR はその回答を記録し、具体化に必要な未承認の案と要確認事項を分けます。
**ユーザー決定が存在することと、本 ADR 全体の承認・実装完了は別です。** Status は Proposed とし、
AI の推奨案を採用済み仕様にしません。既存 ADR の本文・注記、SPEC・CONTEXT の機能状態は変更しません。

正本は #77 本文の「ユーザー回答（2026-10-07）」表、
[2026-10-13 の回答コメント](https://github.com/FYuki/digital-souls-core/issues/77#issuecomment-6129134793)、
[方式と実装時期のコメント](https://github.com/FYuki/digital-souls-core/issues/77#issuecomment-6129195580)です。
日付は正本の回答日（日本時間）を使います。2026-10-07 の本文表には発話の括弧付き原文がなく、
以下では**本文表の記載をそのまま引用**します。2026-10-13 はコメントの「」内のユーザー発話原文を引用します。

## 選択肢

| 方針 | 判断と根拠 |
| --- | --- |
| Binding 完全一致のまま共有しない | 現行契約。2026-10-07 の共有方針と、2026-10-13 の照合範囲変更に対応できない |
| 個人名を長期記憶に保持し、利用時だけ置き換える | 2026-10-13「保存時に代名詞にする」「原文は残さず」に反する |
| 保存時に名前を置き換え、同じキャラクター内で用途に応じて共有する | ユーザー決定の方向。用途・権限・照合・出典契約の具体化は以下の AI 提案と要確認事項 |

置き換え方式は LLM 単独・規則単独を新たに採用するのでなく、ユーザーが指定した組み合わせを
前提とします。NER の製品・モデル・依存の採用は本 ADR で決めません。

## 決定

### 1. ユーザー決定（2026-10-07）

出典は #77 本文表です。引用は当日の記録を保持し、後日の置き換えとの関係を右列に示します。

| ID | 論点 | 本文表の引用 | 後日の決定との関係 |
| --- | --- | --- | --- |
| U1 | 共有の範囲 | 「Bindingの要素をまたいでよい（同じキャラクターが知っていることは参照できる）」 | character をまたぐ共有は指定されていない |
| U2 | 会話履歴 | 「利用者に固定する。他の利用者の会話履歴は参照しない」 | 保存時の名前置換は会話履歴の原文を変更する指示ではない（#214・#215） |
| U3 | Episode・Semantic | 「共有してよい。ただし、個人情報や関係性が明確でない限り個人名を出さない（代名詞に置き換える等）機能が必要」 | 「関係性が明確」の条件は U7 で棄却。名前の制御段階は U8 で保存時に指定 |
| U4 | Fact | 「3と同じ制御を受ける。第三者の名前など、話し手以外の情報を制御する」 | 管理者向け・配信向けの違いは U7 に従う |
| U5 | 会話外の活動 | 「長期記憶になったものは使用してよい。ただし3・4と同じ制御を受ける」 | 話し手の名前・識別を出さない条件は U9 に従う |

### 2. ユーザー決定（2026-10-13）

U7〜U12 と U14 は回答コメント、U13・U15 は方式と実装時期のコメントを出典とします。
表の「内容」は整理であり、解釈が分かれる点を「要確認」へ残します。

| ID | 内容 | ユーザー発話原文 |
| --- | --- | --- |
| U7 | 「関係性が明確」の定義を棄却。管理者向けは利用者が明言した人の Fact、配信向けは抽象化した Episode まで | 「棄却。管理者用であれば、利用者が明言した人のfactを参照可能 配信用では抽象化したエピソードまで（～～と話していた人もいたよ等）」 |
| U8 | 保存時に代名詞・続柄へ置き換え、原文を記憶に残さない | 「保存時に代名詞にする 原文は残さず、代名詞にする（友人、母、兄・・・）」 |
| U9 | 配信・会話外活動では話し手の名前・識別を出さない。管理者向けは言及された場合のみ利用可能 | 「配信・会話外活動：出さない 管理者：言及された場合のみ利用可能」 |
| U10 | 公開の場には追加制限が必要。具体案は未決定 | 「追加の制限必要」 |
| U11 | 名前が残ったままの保存0件を必須ゲートとし、誤陽性はある程度許容 | 「安全側に倒すため、個人名を残したままの保存0、誤陽性はある程度認める」 |
| U12 | 訂正は利用者単位、事実の照合はキャラクター単位へ拡大 | 「訂正は利用者単位に広げて、事実の照合はキャラクター単位」 |
| U13 | LLM による置換と NER・規則による残存検査の組み合わせ | 「組み合わせによる判定でよい」 |
| U14 | 認証 Epic は #77 の後 | 「認証epicは#77の後でよい」 |
| U15 | #77 の決定を #127 内で実装 | 「#127内で修正するようにして」 |

U13 の具体的な工程は #214・#215 に記載されています。ローカル LLM が抽出時に続柄へ置き換え、
置き換え後の保存文と構造化値を NER と辞書・接尾辞の規則で決定論的に検査し、人名らしきものが
残れば保存しません（ABSTAIN）。#215 は原文の個人名を記憶の正本・保存文・構造化値・ログ・report に
残さず、会話履歴の原文を変更しないことを要求しています。誤陽性には過剰な置換・保存見送りを含みます。
これらは工程のユーザー決定であり、NER の候補選定や以下の具体案を承認した根拠にはしません。

### 3. AI 提案（Proposed、未承認）：公開の場の追加制限

ここからはすべて **AI 提案・未承認** です。「推奨」はユーザー決定ではありません。
公開の場・配信・audience が異なる場の扱いについて、次の選択肢を提示します。

| 案 | 追加制限 | 評価 |
| --- | --- | --- |
| A：抽象化のみ | Fact・Semantic を出さず、名前を置き換えた Episode を抽象化して出す | 続柄・場所・日時・他の発言を組み合わせた特定には対応が不足 |
| B：抽象化と組み合わせの制限 | A に加え、特定につながる続柄・日時・場所等を一般化し、話し手や出典の識別を出さない。一般化の安全性が判定できなければ利用しない | **推奨**。U7・U9 を守り、名前以外からの特定にも制限を設ける |
| C：他利用者由来の記憶を一切利用しない | 公開の場では共有を無効にする | 安全側だが、抽象化した Episode の利用もできない |

推奨 B では、公開向けに Fact を添付せず、Episode 内に埋め込んだ Fact の詳細も出しません。
Semantic は第三者に関するものを含め、公開向け共有では出しません。管理者向けの私的な場での
Semantic と会話外活動の内部参照の扱いは Q6 の確認対象です。
話し手の氏名・表示名・利用者 ID・固定の呼び名、照合可能な出典 ID を出しません。
続柄だけでも「その人の兄」などで特定につながる場合は「ある人」「知人」等へさらに一般化し、
根拠のない関係を創作しません。例は合成です。抽象化した文と最終送信内容も検査対象とし、
判定不能ならその記憶を使いません。名前の置換を、機微情報の共有許可とは扱いません（Q10）。

共有の適格性はモデル入力を作る前に Core で制限する案を推奨します。prompt だけで公開範囲を
強制せず、送信時は [ADR 0020 §6](0020-reflection-personality-relationship.md#6-会話外の活動との境界)・
[ADR 0027](0027-tool-use-and-activity-runtime.md)の Gate と流出防止も維持します。
出典側の memory 許可・除外・private 状態と、利用先の memory および送信先の local/external 許可を
それぞれ確認する案を推奨します。共有可能な種別であることだけで、別 Binding の permission を継承しません。

### 4. AI 提案（Proposed、未承認）：置換対象と残存検査

| 対象 | 具体化の案 |
| --- | --- |
| Episode・Fact | normalized_text と 5W 全体。Who だけでなく What の対象、Where の名称、Why の明示理由等に埋め込まれた個人名も対象 |
| Semantic | 保存文と構造化命題の主体・属性・値、直接抽出と一般化の双方。一般化を介して名前を再導入しない |
| 保存文の生成 | 置換・検査した構造化値から生成し、生成後の保存文をもう一度検査。構造化値と保存文の片方だけの合格では保存しない |
| 自由文の引用・説明 | 引用符内も除外しない。記憶側に原文の複写、旧文、元の名前への可逆な置換表を作らない |
| Citation | 履歴原文へのアドレスを保持し、原文本文は複写しない。置換後の文字範囲へ変更しない（次節） |
| 拒否・評価の記録 | matched value・候補本文・例外本文をログや report に残さず、判定種別・規則/モデル版・件数等だけを記録 |

既存の秘密値・直接識別値・意味分類・保存拒否・source 検証は迂回しません。
抽出へのローカル送信前の既存検査を維持し、名前置換で認証情報や機微内容を洗い流して
ALLOW_STRUCTURED にしません。NER・規則の欠落、不正結果、判定不能も保存を止める案を推奨します。
既存判定の DENY_* が優先し、残存検査による ABSTAIN の具体的な enum・理由コードは
#207・#215 で既存契約と整合させます。本 ADR で新 enum は決めません。

**NER・規則の候補（採用未決定）**：すべて、モデル・辞書をローカルに配置し、実行中に外部通信・
自動ダウンロード・外部 fallback をしない構成を条件に比較します。
以下は検討候補名と比較観点であり、この作業では導入・実機検証・性能の断定を行いません。

| 候補 | #215 で比較・確認する点 |
| --- | --- |
| 日本語 NER のライブラリ候補：GiNZA / spaCy のローカル pipeline | PERSON 相当のラベル、漢字・かな・ローマ字・単名・別名の検出範囲、モデル/辞書版、CPU負荷、依存・ライセンス、オフライン固定の可否 |
| 日本語 NER のモデル候補：Transformers 等のローカル token classification | 日本語モデルの選定、token境界・分割名、閾値・数値計算の再現性、モデル容量、追加依存、ライセンス、ローカル読込の強制 |
| 辞書・接尾辞の規則（NER と併用） | 人名辞書、呼称の前後、「さん・くん・ちゃん・様・先生」、空白や表記ゆれ。姓だけ・接尾辞なしの見逃し、一般名詞の誤陽性、辞書更新と版固定 |

NER は、固定したモデル・辞書・推論設定から決定論的な残存判定へ接続する候補です。
候補の検出なしを完全な匿名化の証明とはしません。規則との併用による見逃し・過剰判定を合成データで比較します。
依存の追加は製品の言語・依存の決定に関わるため、**採用は #215 でユーザー確認して決めます**。
この ADR はバージョン・ライブラリ・製品言語を選定しません。

評価は U11 の「個人名を残したままの保存0件」を独立した必須ゲートにし、他の品質で相殺しません。
AI 提案として、保存文・構造化値・正本・ログ・report の各漏出を分け、保存件数と残存件数、過剰置換と
保存見送りを別集計することを推奨します。常に保存を見送った結果を品質合格にしない基準は Q8 で確認します。
#206 の合成ケースと実行前固定の期待値、#212・#213 の評価へ引き渡し、この Issue ではケースを変更しません。
[ADR 0032](0032-privacy-classifier-evaluation.md)の分類器品質 FAIL は、名前置換の追加で解消したとは扱いません。

### 5. AI 提案（Proposed、未承認）：Citation と共有時の出典

[ADR 0016 §5](0016-memory-kinds-and-records.md#5-出典版識別子)と記憶APIの `Citation` は、
出典の Binding・SourceVersion・話者・履歴 message 内の半開文字範囲 `[start, end)` を持ちます。
**Citation が指すのは会話履歴の原文**です。保存時に記憶の名前を置き換えても、出典の原文を
置換したものに変更せず、置換後の保存文に合わせて引用 offset を付け直しません。
内部で根拠との対応を検証できることと、閲覧者へ原文を開示できることを分ける案を推奨します。

- Citation は内部の根拠検証・版照合・撤回・再構成用に保持します。別利用者への共有を理由に、
  出典履歴の read/export 権限や、その利用者の prompt 履歴への混入を許しません。
- [ADR 0022 §3](0022-memory-retrieval-from-records.md#3-モデル向け-contextu3)のとおり、引用原文・
  逐語 user_evidence はモデルに渡しません。他の利用者との会話へ引用原文を出さないことを維持します。
- 共有時は、保存 ID・利用者 ID・出典 Binding・原文をモデル/閲覧者に出さず、検査済みの記憶文と
  要求ごとの一時 memory_ref を用いる案を推奨します。conversation_ref・turn 等の出典 metadata を
  共有時に省略するか、一時参照に限定するかは Q7 で確認します。内部の出典追跡は省略しません。
- 他利用者が使う派生記憶も、出典削除・private 化で即時に利用停止し、適格な残存出典から再構成します。
  再構成した文・構造化値も名前の残存検査を通します。共有先の会話や検索結果を、消えた出典の代用にしません。

別 Binding の Citation・依存関係を現行の型・schema・port が拒否する点は、Q4 で承認待ちです。
出典を共有先 Binding に付け替えて現行検査を通す案は推奨しません。

### 6. AI 提案（Proposed、未承認）：認証 Epic に求める要件

以下は認証 Epic への要求であり、認証方式・API field・audience 値・トークン・役割モデルの設計ではありません。

- 利用者、キャラクター、管理者向け/配信向け、公開性、audience が異なる場、会話外活動の区別を、
  信頼できる形で Core へ渡せること。U9 の「言及された場合」を確認する根拠も必要（Q1）。
- audience 等を判定根拠にする場合も、HTTP 本文の自己申告や LLM の判断だけで管理者権限を付与しないこと。
  管理者向けかつ公開の場なら、公開向けの強い制限を適用できること。
- **推奨**：管理者/配信の識別が欠落・不正・不明なら、最も制限の強い配信向けの扱いへ縮退する。
  さらに利用者・character・保存/検索/送信の認可自体が不明なら、共有を含む当該操作を拒否する（fail-closed）。
  配信向けへの縮退だけで既存 permission を付与しないこと。
- Core が参照・送信の各境界でこの区別を再検証でき、未認証の間に管理者向け例外を有効にしないこと。

具体的な識別機構は U14 に従い後続 Epic で扱います。#127 の文書承認は認証の実装済みを意味しません。

| [ADR 0017 §2・§3・§4・§5・§7](0017-memory-formation-admission.md)：同一 Binding/スレッドの照合と別 Binding の照合・統合拒否 | U12 により照合を character 単位、訂正を利用者単位へ広げる。統合・consolidation まで許す範囲は Q3・Q4 で確認。名前置換・残存検査を保存判定へ接続するが、ALLOW_STRUCTUREDのみ保存、DENY優先、出典・冪等性は維持 |
| [ADR 0018 §3](0018-memory-retrieval-context.md#3-候補の取得と再検証)：Binding 検証を含む候補取得・再検証 | 条件付き共有の適格性へ変更。query gate、失効・版・privacyの再検証、順位、障害時の記憶なし継続は維持 |
| [ADR 0019 §1・§4](0019-memory-correction-invalidation.md)：知識の照合・参照・訂正を同じ Binding 全体へ適用、別 Binding 参照を拒否 | U12 に従い照合・訂正を分ける。参照と失効の跨ぎ方は Q4。U6 に従い共有先の派生結果にも即時停止・残存根拠からの再構成を適用。削除・private化・版失効の規則は維持 |
| [ADR 0022 §1・§3](0022-memory-retrieval-from-records.md)：Binding 完全一致の検索、sources metadata | 検索の共有適格性と公開向けの添付Fact制限、出典metadataを承認範囲で変更。Episode・Semanticの候補元、Factの非独立embedding、原文非注入、一時参照、dispatch guardは維持（Q5・Q7） |
| [ADR 0020 §6](0020-reflection-personality-relationship.md#6-会話外の活動との境界)・[ADR 0027](0027-tool-use-and-activity-runtime.md) | 記憶の条件付き利用と話し手非開示を補足。CoreのGate・送信直前検査・インジェクション境界・実行基盤の責務は置換しない |
| [ADR 0032](0032-privacy-classifier-evaluation.md) | LocalClassifier評価の分類・ABSTAIN10%未満の契約を自動変更しない。名前残存の必須ゲートと保存判定のABSTAINは別の評価対象（Q8） |

Accepted 後の SPEC・CONTEXT・記憶API・privacyガイドの同期は、承認内容と実装状況を分けて行います。
SPEC の「別 Binding の混入0件」は、許可された共有と無認可の混入を区別する受入条件への整合が必要です。
本 ADR の Proposed 段階では、その受入条件を緩めません。

## 要確認（すべて AI の選択肢・推奨、未承認）

各項目は、ユーザー決定どうし・既存契約の解釈が分かれる箇所です。推奨を決定として実装しません。

| ID | 論点 | 選択肢 | AI の推奨案と理由 |
| --- | --- | --- | --- |
| Q1 | U8 の原文非保存と U7・U9 の管理者向け人物/話し手参照の両立。「言及」は誰がいつ行うか | A：置換済み Fact と現在の明示言及だけを使う。B：管理者向けに出典履歴を読み名前を復元。C：名前の対応表を別保存 | **Aを推奨**。保存済み記憶では「友人」等と根拠の範囲だけを参照し、名前を復元しない。現在の認可された入力で明言した人と対応が確認できた場合の、一時的な利用だけを承認候補とする。曖昧な続柄から同定しない。Bは他利用者履歴の非共有、Cは原文非保存と衝突。誰によるどの言及が十分かはユーザー確認が必要 |
| Q2 | 「訂正は利用者単位」で外す Binding 要素、他利用者の Fact を訂正できるか | A：subject・character を残し client・audience・thread を外す。B：subject だけを残し character もまたぐ。C：character 内で他利用者由来の Fact も上書きする | **Aを推奨**。同じ利用者・キャラクターの出典に由来する Fact/知識をスレッド・入口越しに訂正し、他利用者の根拠は上書きしない。共有から訂正権限を導かない。混合根拠の派生記憶は利用停止・再評価する。characterを残す解釈、Semantic訂正や管理操作を#210でどこまで扱うかは承認が必要 |
| Q3 | 「照合はキャラクター単位」は候補の比較だけか、別利用者・別スレッドの Fact 統合まで含むか。名前置換後の同一人物をどう確かめるか | A：characterだけを一致させ比較対象を広げ、統合は根拠確認済みのみ。B：同じ続柄や似た5Wを同一人物/Factとして統合。C：比較対象は広げるが別Binding統合は当面行わない | **Aを推奨**。subject・client・audience・threadを候補制限から外すが、unknown同士・同名だけ等の不一致規則は維持。「母」「友人」が同じだけでは人物・出来事を同定しない。根拠が不足したら別Factを保持し、訂正権限はQ2で別判定する。新しい人物IDや可逆な名前表を暗黙導入しない。#127本文の別スレッド統合の範囲外との整合も確認する |
| Q4 | Binding ごとの正本・Citation・同一Binding依存/transaction契約と、character単位の比較・共有・撤回の関係 | A：出典Bindingの正本を保ち、認可された共有の適格性と版付き参照を別に扱う。B：正本をcharacter単位へ再配置。C：共有先へ記憶を複製 | **Aを推奨**。所有・訂正・出典撤回の根拠を保ち、共有先への複写や付け替えで撤回漏れを生まない。ただし現行の別Binding引用/参照拒否、port、lock、schema、跨ぐ依存の即時失効をそのままでは使えない。契約変更・schema要否と担当を承認後の実装Issueで明示し、SQLの検索条件だけを外さない |
| Q5 | ADR 0022 の共有検索をどの Issue で実装するか。#209〜#215 に明示担当がない | A：#127に共有検索・context・guardの子Issueを追加。B：#209/#210/#215へ範囲追加。C：後続Epicへ延期し#127では共有未実装とする | **Aを推奨**。U15に沿い#127内で明示担当を設け、形成/置換・契約変更後、統合受入の前に接続する。Fact照合の拡大だけでは検索は共有にならない。本IssueではIssue追加や範囲変更を実行せず、監督が確認する |

| Q7 | 共有時にsources metadataをどこまでモデル/閲覧者へ渡すか。出典参照で話し手の識別が可能にならないか | A：共有時はmemory_refのみ、出典metadataはCore内部。B：要求ごとの一時conversation_refと版等も渡す。C：元のBinding/IDを渡す | **Aを推奨**。Citation原文非開示とU9を守り、別の情報との突き合わせを減らす。内部の版・epoch・全引用の検証と撤回は維持。Bを必要とする説明用途があるなら開示項目と権限を別確認する。Cは推奨しない |

## 範囲外

- コード・schema・評価ケース・依存の変更、データ移行・実環境操作、実モデル評価。
- ADR を Accepted にすること、既存 ADR の本文改変や現段階の置換注記、SPEC・CONTEXT の状態変更。
- 認証と audience 識別の具体設計・実装。管理者向け例外を認証なしで有効にすること。
- 別キャラクターの共有、人格・Relationship の所有境界変更、名前の対応表や人物同定schemaの採用。

## 影響

#214 のユーザー承認が #209・#215 の前提で、#215 は #209 と並行または組み込みで進めます。
[#209 の追加コメント](https://github.com/FYuki/digital-souls-core/issues/209#issuecomment-6129194863)は名前置換との接続を、
[#210 の変更コメント](https://github.com/FYuki/digital-souls-core/issues/210#issuecomment-6129195224)は照合・訂正の範囲拡大と承認後の実装を指定しています。
[#127 の補足](https://github.com/FYuki/digital-souls-core/issues/127#issuecomment-6128865826)の timer・Core台帳/drain の責務は維持します。

保存時の名前置換で、管理者が後から元の名前を記憶から復元することはできなくなります。
続柄の重複で照合を見送る件数や誤陽性が増える可能性があり、0件の保存漏出ゲートと有用性を別に評価します。
名前を消しただけで安全な共有は完成せず、共有検索の担当（Q5）、出典と依存の契約（Q4）、
公開向け制限・信頼できる用途識別の要件の承認と実装が必要です。
文書検証の成功を、形成・共有・認証・名前検出の実モデル品質や実環境受入の PASS と扱いません。
