# ADR 0035: MVP のクライアント構成（Web・ネイティブ・CLI）

Status: Proposed

日付: 2026-10-17

関連: [ADR 0025](0025-shared-runtime-interfaces.md)、[ADR 0036](0036-mvp-api-keys-and-users.md)、
[ADR 0037](0037-message-level-conversation-history.md)、[ADR 0038](0038-mvp-prompt-window-and-input-scan.md)

## 背景

2026-10-17 にユーザーは、あるべき姿を一から考え直し、MVP の要件を次のとおり示しました。

1. Web、CLI、PC のネイティブアプリから、同じキャラクターカードの応答を得られる。
2. 長期記憶を作るために、応答をバックエンドへ保存できている。
3. Web とネイティブは会話履歴を共通にする。
4. 短期の記憶として、直近 N 往復のやり取りを参照できる。

続けて、次のとおり回答しました。

- CLI の履歴は別でよい。CLI は主にテストで使う。
- 認証はバックエンドが発行した key を登録する簡易なものでよい。
- 会話は複数持てる。既定では、最後にやり取りした会話を再開する。
- Web は同じ PC から使う。使うとしても Cloudflare Tunnel などのプライベートネットワークの中から。
- ネイティブアプリは、Web の画面を Tauri で包む案（推奨案）でよい。
- 流用できる FE の素材が少ないなら、FE は作り直してよい。

既存の資産を確認した結果（2026-10-17、静的な確認のみ）は次のとおりです。

- PoC（公開 `FYuki/digital-souls`、revision `fce7382884d981c42be7fbd3ddaffe7469e27588`）の FE は Svelte 4 で約3.5万行です。
  LiveKit・音声・アドオン・記憶管理・画面認識が中心で、`App.svelte` にまとめて組み込まれています。
  チャットは応答の全文を JSON で受け取る方式で、SSE、認証、最後の会話の再開、ネイティブの包装はありません。
  会話の一覧・名前の変更・削除の部品はありますが、音声の表示・LiveKit の型・UI 設定に依存しています。
- PoC の BE は SQLite と往復単位の保存で、MVP の要件（発言単位の保存、key の認証、SSE、PostgreSQL）を満たしません。
- Core（main `b062a49`）は Card の固定・Card のハッシュ、stream に対応した会話履歴 API、PostgreSQL、token 予算を持ちます。

## 選択肢

| 案 | 判断 |
| --- | --- |
| PoC の FE と BE から始める | 不採用。BE の保存・認証・SSE を作り直す必要があり、音声や活動との結合を外す手間が加わる |
| Core を BE にし、PoC の FE を改修する | 不採用。チャットの経路（SSE・認証・再開）を作り直すうえ、音声などの結合を外す手間が大きい |
| Core を BE にし、FE は作り直す。ネイティブは同じ FE を Tauri で包む | 採用を提案 |
| ネイティブを別の UI 技術で作る | 不採用。画面のコードが2つになる |

## 決定（提案）

### 1. バックエンドは常駐する Core の1つ

Web、ネイティブ、CLI は、いずれも同じ常駐 Core へ接続する薄いクライアントにします（ADR 0025 の A 案のとおり）。
キャラクターの Card、プロンプトの組み立て、会話履歴、推論先の設定は Core だけが持ちます。
クライアントは Card やプロンプトを持たず、組み立てもしません。

### 2. Web の FE は作り直す

PoC の FE はコピーもフォークもせず、新しく作ります。見た目の参考にするのはかまいません。
MVP の画面は次に限ります。

- key の登録（初回）
- 会話の一覧、新しい会話の作成、会話の削除
- 最後にやり取りした会話の自動の再開
- 発言の送信と、SSE による応答の逐次表示
- キャラクターの静止画

音声、アバターの動き、記憶の管理画面、ツール、通知は MVP の範囲外です。

FE は Core とは別の新しいリポジトリに置き、Svelte＋Vite＋TypeScript で作ります（2026-10-17 のユーザー回答「提案内容で良い」）。
リポジトリ名と公開範囲は、リポジトリの作成時にユーザーが決めます。Core の範囲（README の「UI は Core の対象外」）は変えません。
Core は、ビルド済みの FE を静的ファイルとして同じオリジンから配信するだけにします。

### 3. ネイティブは同じ FE を Tauri で包む

ネイティブアプリは、Web と同じ FE のビルドを Tauri で包みます。画面のコードは1つです。
Core への通信は Tauri 側の HTTP を使い、ブラウザーの CORS に依存しません。key は OS の資格情報ストアに保存します。
この通信方式で SSE を逐次受け取れるかは、実装の Issue で最初に確認します（未検証）。

### 4. CLI はテスト用の薄いクライアント

CLI は Core のリポジトリに置き、Core の HTTP API を呼ぶだけにします。主な用途はテストです。
CLI は Web・ネイティブとは別の利用者として key を発行し、履歴を分けます（[ADR 0036](0036-mvp-api-keys-and-users.md)）。

### 5. 接続の範囲

Core に接続できるのは、同じ PC か、Cloudflare Tunnel などのプライベートネットワークの中からだけです。
インターネットへの一般公開はしません。PC の外から接続する場合は、トンネルの前段にアクセス制御
（Cloudflare Access 等）を置くことを運用の条件にします。トンネルは、それだけでは公開の URL になるためです。

## 影響

- FE とネイティブは新しく作るため、PoC の画面の機能（音声など）は MVP では使えません。
- Core は静的ファイルの配信と、許可するホスト名の設定が必要になります（現在は localhost のみ）。
- 3つのクライアントが同じ API を使うので、Card のハッシュ（`X-Character-Card-SHA256`）で同じ Card かを確かめられます。

## 範囲外

- 音声、アバター、記憶の管理画面、会話外の活動、Discord 等の bot。
- 長期記憶の形成・検索（[Epic #127](https://github.com/FYuki/digital-souls-core/issues/127) で扱う）。
