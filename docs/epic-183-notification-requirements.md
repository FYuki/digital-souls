# Epic #183 通知基盤の要件指示書

## 状態・目的

2026-09-16のgrill-meで合意した要求を、既存の通知／会話分離契約と合わせて整理する。
**設計合意であり、通知機能の実装・受入完了を示さない。** 進捗の正本は[親Issue #183](https://github.com/FYuki/digital-souls/issues/183)と子Issueとする。
会話・LLM・音声sessionなしでも外部イベントや非同期結果を通知として保存・確認できるようにする。
通知の寿命と提供元の情報・会話からの再取得を分離し、個別通知の確認と利用者による通知対象の選択を可能にする。

## 要件

### 個別通知と冪等性

- 通知レコードは個別保存する。同じ通知元・resource・event typeでも複数の通知を一つへ集約しない。
- 同じイベント・結果revisionの再配送は重複作成しない。別イベント・別実行結果は別通知とする。
- 集約数・集約revisionは不要。出典のrevisionと既読操作の対象識別は維持し、通知の集約と混同しない。
- 担当・所有者・公開範囲・接続・Task／実行回の識別と分離、通知保存とconsumer進捗の整合を維持する。
- raw本文・結果・secret・raw endpointを通知DB・通常log・履歴・RAGへ自動保存しない。

### 保持・削除と再取得

- 各通知の初回保存から既定30日保持する。発生時刻やブラウザでの初回表示からは数えない。
- 再配送や既読／非表示操作で初回保存時点や期限を延長しない。
- 件数上限では未読を含め、初回保存の古い順に30日未満でも削除できる。UIで保持期間内の履歴の不足を示す。
- 通知の期限切れ・件数上限による削除を、元処理の取消し・監視解除・会話取込・報告完了へ変換しない。
- 会話などからの再取得に必要な依頼・実行・Task／rule・登録時対象参照は通知から独立して管理する。
- #363は通知レコードの存在を取得の必須条件とせず、有効なCore管理参照から現在権限で取得できるようにする。
- 参照の保持は依頼・会話側のprivacyと削除規則に従う。削除された会話・担当を復活させず、全通知の無期限保存を作らない。
- 提供元が正本を保持している場合に取得できる。監視は最新状態、単発処理は元の実行・成果物の結果を取得する。
- 提供元の削除・期限切れ・権限喪失・取得不能は明示し、過去結果を別実行や推測で埋めない。
- 削除済み通知IDや引用された任意IDだけを取得権限にしない。登録時担当・対象、Gate、現在権限、継続予算を検証する。

### 初回UIと通知設定

- 会話非依存の時系列一覧と、通知元・担当キャラクター・未読による絞り込みを提供する。
- 通知元ごとに束ねる表示は追加候補。キャラクターの要約回答は後続の会話側の表現であり、通知レコードの統合ではない。
- 通知元・通知種類ごとにユーザーがON／OFFを変更できる設定を初回に含める。
- 未設定はignore、判定失敗・不正な権限／参照はfail-closed。ONでも認可を省略しない。
- OFFは通知生成だけを止め、元の処理・監視・共有source取得・保存済み通知を変更しない。
- 再ON以降に届く分だけを通知する。OFF中に受け取った分は再配送・再起動を含め遡って通知にしない。
- OFF中の分を保留通知として溜めない。通知consumerの処理判断と進捗を整合させ、会話consumerの進捗・報告状態とは分ける。
- 細かな条件式やキャラクターによる通知要否の判断は初回の対象外とする。

### 継続する既存契約

- 通知の生成・保存はforeground、active conversation、idle、音声session、LLMの稼働に依存しない。
- ブラウザ終了・端末オフライン中もBackend稼働中は取得・保存する。復帰・一覧取得だけでは既読にしない。
- Backend停止中の未取得分・復元不能な欠落は#187の契約に従う。履歴が全て揃うと誤表示しない。
- 詳細の提示・確認または明示操作を既読の境界とし、prefetchや取得成功だけでは既読にしない。取得失敗も自動既読にしない。
- 既読・未読・非表示はユーザー単位で管理し、競合や複数端末の操作でも新着の未確認通知を消さない。
- 通知閲覧・通知設定はキャラクターへの文脈取込ではない。別キャラクターへの暗黙共有を行わない。
- 取得はLLM非依存でも既存の共有Gate・認可・binding・snapshot・有限取得と継続予算を通す。

## 受け入れ条件

1. 同じsourceの異なるイベント・実行結果を個別保存し、同一イベント・結果revisionの再配送では重複させない。
2. 初回保存から30日で期限切れになる。発生時刻の古いイベントでも保存時点から数え、再配送・既読操作で延長しない。
3. 件数上限では未読を含め古い順に削除し、期間内の履歴の不足をUIへ伝える。
4. 通知削除後も有効な独立参照から内容を取得でき、現在権限の失効・提供元の結果削除・期限切れでは取得不能になる。
5. 通知削除が依頼参照の連鎖削除、Task取消し、監視解除、報告完了にならない。#183では契約を、#365では会話接続を検証する。
6. 時系列一覧・通知元／担当／未読の絞り込みが会話・LLMなしで利用できる。
7. 通知元・通知種類ごとにON／OFFを設定でき、OFFでも元処理・共有取得・保存済み通知を変えない。
8. OFF中に受け取ったイベントを再ON・再配送・再起動で遡及通知せず、新しく届く対象イベントは通常Policyを通す。
9. 通知保存途中の障害でも進捗だけを進めて取りこぼさず、既読操作と新着の競合でも操作対象外を既読にしない。
10. raw本文・結果・secretを自動永続化せず、別ユーザー・別担当の権限を借用しない。会話統合未実装でも#183を受け入れられる。

## 制約・対象外

Event transport・復旧本体、Task lifecycle・scheduler、外部write／delete、OS push・メール配送は追加しない。
登録UI／schedulerの新規開発と、今回追加する通知ON／OFF設定UIは区別する。
バナー・通知音・通知元で束ねる表示は追加候補。要約回答・会話からの実際の取得導線・自発発話は#364側で扱う。

## 実装で具体化する事項

- 件数上限の具体値と適用単位は未指定。想定流量・保存容量と、他ユーザー／担当への影響を評価して根拠とともに定める。
- 具体的なAPI・型・DB配置・設定の適用主体・既存Policyとの解決順序、同時刻の順序は既存契約に合わせる。所有者・公開範囲を越えて設定を適用しない。
- OFF中の判断と再配送の整合、有限な重複防止情報、削除後の参照・履歴不足の表現を具体化する。通知削除で再配送の重複防止を破らない。
- 合意した保持・分離・認可・非遡及の振る舞いを変更する必要が生じた場合は、その影響を示して再整理する。
