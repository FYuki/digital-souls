# CUDA Graph入力上限の修正と実ブラウザ再測定（2026-09-19）

[実装PR #446](https://github.com/FYuki/digital-souls/pull/446)とは分離して、
[原因診断と全試行のmanifest](../artifacts/irodori-graph-capacity-20260919/manifest.json)を保存する。
従来の64MiB版は[前回の実ブラウザ結果](irodori-graph-browser-20260919.md)を上書きせず保持する。

## 原因の確認

初期試作は2形状をGraph化していたが、#442の実装版は1形状しかGraph化していなかった。
計測で通常CFGの入力tensor合計が214322028〜214385004 bytes（約204MiB）と判明した。
64MiBの入力上限ではCFG側が通常forwardへ戻り、速度改善を制限していた。

CPU側の診断では、要求あたりのVRAM照会は約0.12ms、signature計算約2.9ms、
入力容量確認約1.0ms、入力clone約0.9ms、入力更新約14.1msだった。
計測instrumentationを含む値であり、GPU演算時間とは異なる。
これらを削除して品質・復旧境界を緩める必要性は確認しなかった。

64/128MiBの5文×3回の対比較では、双方ともGraph化1形状のままで、
中央値653.41ms / 646.17ms。128MiBでは通常入力を収められなかった。
64/256MiBの同条件対比較では、Graph化1→2形状、中央値
**709.19ms→557.86ms（約21%短縮）**。対応音声のframe数は全件一致した。
短文のPCM差は通常反復にも生じ、聴感同等性を証明したとはしない。
両比較は別runであり、異なるrunの中央値を組み合わせて改善率を算出しない。

## 実装の変更と検証

#446は上限を256MiBへ修正する。機能は既定OFFを維持し、
最大2形状、入力容量＋1GiBの空きVRAM確認、要求終了時の解放、
全入力の更新、出力の独立性、異常時のworker破棄を維持する。
capture中の一時VRAM使用量が厳密に256MiB以内という意味ではない。
40 steps、採用声・caption・seed・speed、BF16、duration推定は変更しない。

実測入力がcaptureへ進まない回帰を修正前に再現した。
修正後は関連単体49件とirodori_serviceのmypy、diff確認が成功。
固定commit 59a7d49157e60867b399b0b2b9e2e4fb46d13a68から
image sha256:1584e3832accdc66e1ad91a96d386a1f14e872a8badf5e844d6837fe4ff136e0をbuildした。
専用TTSの実合成readinessと、コンテナ内のMAX_INPUT_BYTES=268435456を確認した。
