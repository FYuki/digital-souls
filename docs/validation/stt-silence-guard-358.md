# #358 無音の誤認識による割り込みの修正

## 症状と原因

光織の再生中に、発話していないのに「ご視聴ありがとうございました」が認識され、
`barge_in`で応答が中断された。devの診断ログで取消理由を確認した。
同じ共有Whisperへ0.5秒／2秒の無音、低レベル雑音、単一周波数音を送ると、4条件とも同じ定型句を生成した。
Whisperの無音確率は約0.86〜0.92だったが、文字列の確率が高いため標準の無音除外が働かなかった。
実際のマイク入力が上流VADを通過した理由は、この検証だけでは特定していない。

## 修正

共有Whisperの通常認識で、区間の`no_speech_prob`が0.6を超える結果を採用しない。
非有限値・範囲外の確率も採用しない。0.6は固定版faster-whisperの既定の無音閾値と同じで、
認識文字列の確率による上書きを許さない。文字列の禁止リストは設けない。
音声区間を切り取らず、元のPCMとモデル・デコード設定を維持する。
起動時は従来どおりGPU推論を最後まで実行し、結果を利用者へ公開しない。

相槌は既存の`backchannel`として再生を継続する。空の結果は`indeterminate`となり、
暫定認識・確定認識とも割り込まない。「はい、でも質問があります」などは発話権取得の対象のままとする。
中断診断には理由と再生済み連番のみを残し、本文・音声は追加記録しない。

## 検証

- 関連unit test: 65件成功。無音の除外、通常語句と実際の定型句の保持、異常確率の除外、
  空の暫定認識では再生を継続し、後続の明確な発話では割り込むことを確認。
- GPU実サービス比較: 合成音声のみ25条件を旧版・修正版へ同じPCMで送信。
- 無音・雑音4条件: 旧版は4件とも定型句、修正版は4件とも空。
- 発話権取得10条件: 10件とも旧版と同じ認識。元からある「ストップして」の認識誤りは改善したと扱わない。
- 相槌10条件: 8件は同じ認識。1件は旧版から空。別の1件は旧版の「フゥー」を無音確率0.867で除外。
  相槌をすべて正しく文字起こしできることの証明ではない。少なくとも「うん」「はい」は保持した。
- 実際に発声した「ご視聴ありがとうございました」: 旧版・修正版とも認識。
- 最初に試した既定VADの区間切り出しは「うん」「はい」を失ったため採用しなかった。

結果: [合成音声の比較](../artifacts/stt-silence-guard-20260916.json)。
これはSTTの回帰検証であり、利用者の実マイクでの中断解消や全音声品質ゲートの合格とは区別する。
