## 記憶形成停止と空状態の確認

350-memory-off-0919-01はwarmup 1件成功後、最初の計測で空状態検査に失敗した。
warmup後のmemory_response_originsが1行残るためであり、予定した計測3件のうち1件失敗、
残り2件は到達しなかった。検査を緩めず、正式runnerと同じ独立data root方式で次のrunを実行した。
初回のinference log観測0件はログ出力を取得できなかったため、推論request 0件の証明には用いない。

350-memory-off-0919-02は新規data root、warmupなし、独立1試行で成功した。

- 開始時の履歴・記憶の対象tableは全て0行、RAG無効。
- 実起動receiptで形成・統合の両方が停止。初期状態hashにも停止policyを含む。
- 終了後の形成予約はPENDING、attempts 0、completed revision 0、leaseなし。
- 専用Backendのdata mountを照合しpublic inference healthを166回観測。
  chatの更新がある一方、memory-extraction / memory-consolidation / embeddingの時刻は不変。
  semantic-extractionは未設定のまま。これは全HTTP requestをwire captureした証拠ではない。
- 初期状態・停止receipt・予約状態とhealth観測を合わせた限定的な実接続確認であり、
  記憶形成の性能影響調査には拡張しない。

## 空状態1試行の応答速度

発話終了の因果時計区間からAudioWorkletでの実出力開始までを使用する。
manifestに残る送信基準のlatencyMs（約2,041ms）を今回のTTFAに読み替えない。

| 観測 | 結果 |
|---|---:|
| 利用者発話終了→実再生開始 | **2,975.83〜2,977.43ms（目標未達）** |
| 開始準備 | 2,369.80ms、1回で成功。TTFAとは別計測 |
| STT処理 | 156.93ms |
| prompt準備 | 606.27ms（うちtoken estimate 3回、合計603.64ms） |
| LLM request→first token | 331.48ms |
| 先頭TTS | 960.70ms |
| 全文出力 | 340,800 samples、gap 0、Session終了確認 |

工程時間は同一server時計内の差分であり、異なる時計を直接引き算していない。
並行処理や工程外の待ちを含むため、工程表を単純合算してTTFAと同一視しない。
1試行からp95や安定した2秒達成を主張しない。

## Ollama内部時間の追加診断

会話とは別に、共有Ollama 0.32.5へ合成短文を5回直列送信した。
[診断JSON](../artifacts/voice-quality-350-ollama-load-20260919.json)に全件を保存した。
開始前のモデル一覧は空で、1件目は約6.06秒、うちload_durationは約5.99秒だった。
続く4件もload_durationは252.68〜259.47ms、リクエスト全体は287.90〜298.44msだった。
終了時には同じdigestのgemma4:e4bが8,192 contextで常駐していた。
これは正式会話試験の分母に加えない。

[同版の公式実装](https://github.com/ollama/ollama/blob/v0.32.5/server/routes.go#L2272-L2463)では、
load_durationはrequest開始からscheduleRunner完了までを含む。
モデル定義・capability確認等も含まれるため、値だけで毎回のGPUモデル再ロードと断定しない。
[モデル情報の読込実装](https://github.com/ollama/ollama/blob/v0.32.5/server/images.go#L594-L645)には
GGUF metadataの読込があり、常駐後の処理コストの調査候補とするが、原因はまだ確定していない。
共有Ollamaの設定・バイナリ・モデルは変更していない。
