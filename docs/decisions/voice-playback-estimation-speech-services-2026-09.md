# 再生済み範囲のBackend推定とSTT／TTS接続方式（2026-09）

## 状態・適用範囲

**ACTIVE**。2026-09-27〜28のアーキテクチャ見直しで合意した判断。FE／BE分離に向けた音声とCoreの契約を定める。
次の既存ADRの該当部分を置き換える。それ以外の判断は維持する。

| 既存ADR | 置き換える範囲 |
|---|---|
| [Backend集約](voice-backend-authority-2026-09.md) 決定2 | FEが実再生観測を所有し、その報告を正とする前提。FEの観測は任意の補正値とする |
| [LiveKit transport](livekit-transport-2026-08.md)「応答生成と出力完了の境界」 | ブラウザの全出力確認を待って応答を完了させる規則と、10秒の確認待ち |
| [共通client](conversation-session-client-2026-09.md) `interruptResponse` | 中断時にFEが送る再生済みprefixを正とする前提 |

BEによる音声活動・正式発話境界・take-turnの所有（Backend集約ADR 決定1・3）、
[複数入口ADR](multi-entry-character-core-2026-09.md) §1の「Coreが受け取るのは確定入力・割込・取消・実再生済み範囲」という境界は維持する。
実再生済み範囲は本ADRの推定値としてVoice adapterがCoreへ渡す。

## 決定時点の前提

- #358でVAD・発話区間・take-turnをBEへ移し、#424（2026-09-20クローズ）で性能受入を行った。
- FEは中断時に`last_played_audio_sequence`（再生済みの音声区間番号）を報告し、Coreはそれで履歴に残す範囲を決めていた。
- `ResponseCompletionPort`はブラウザの全出力確認を待って応答を完了させていた。
- BEは応答音声を区間ごとに合成し、`paced_audio`で10ms単位・最大1秒のqueueからWebRTCへ送出していた。
- FE／BE分離を進めるにあたり、再生イベントをFEから返す実装がFEとBEを密結合にしていた。
- STTは共有Whisper HTTP service、TTSはVOICEVOX・Irodoriを、それぞれ自作clientで呼んでいた。

## 決定

### 1. 再生済み範囲はBEが送出位置から推定する

- 割り込みの時刻は、BEのtake-turn判断で確定した時刻とする。
- 再生済み位置 = その時刻までにBEが送出した音声の位置 − 下り遅延 d。
- 下り遅延 d は、ネットワーク・受信側のジッタバッファ・再生デバイスによる遅延の推定値とする。
- 推定位置は音声区間の境界に丸め、区間に対応する本文までを再生済みとして履歴に残す。
- 判断が曖昧な場合は**短い側に丸める**。言った内容を言っていないと扱う誤りは言い直しで済むが、
  聞かせていない内容を言ったと扱う誤りは、ユーザーが聞いていない前提で会話を進めてしまう。

### 2. FEの再生観測は任意の補正値とする

- FEから再生済みprefixや再生完了の通知が届いた場合は推定の補正に使ってよい。
- BEはFEの通知を待たない。通知が届かないことを失敗として扱わない。
- 新しいクライアント（Desktop等）は再生イベントを実装しなくても音声会話に参加できる。

### 3. 出力完了も推定で判定する

応答の出力完了は「BEが残りの音声を送出し終えた時刻 + d」とする。ブラウザの全出力確認を待たない。

### 4. 割り込み判断は自前で維持する

VAD、発話区間、相槌とtake-turnの判断、再生の停止は、音声会話の体験に直結するため自前の実装を維持する。
フレームワークを使う範囲はSTT・TTSへの接続に限る。

### 5. STTは既存ライブラリで接続する

- STTはOpenAI互換の文字起こしAPI（`/v1/audio/transcriptions`）として提供し、既存のclientライブラリ
  （例：LiveKit Agentsの`openai.STT`の`base_url`指定、OpenAI SDK）から呼ぶ。自作clientを保守しない。
- 発話区間はBEのVADで確定するため、発話ごとの一括文字起こしで足りる。ストリーミングは必須にしない。
- Whisperモデルは共有サービスが所有し、Backendのプロセスへ読み込まない（[環境分離ADR](local-dogfood-environment-2026-08.md)のGPU二重ロード回避を維持）。

### 6. TTSはエンジンごとの薄いAdapterとする

- TTSはキャラクターの声そのものであり、エンジン固有の設定（Irodoriのseed・num_steps・caption等）と
  区間単位の取消が体験に影響する。汎用ライブラリやOpenAI互換APIへの統一を必須にしない。
- CoreからはTTSのポートだけに依存し、エンジンごとの差はAdapterに閉じ込める。

## 採らなかった案

| 案 | 採らない理由 |
|---|---|
| FEが送信済みのテキストを再生済みとして扱う | 生成は再生より先に進むため、聞かせていない内容まで履歴に残る |
| FEの実再生範囲の報告を必須のまま維持する | FE／BEの密結合が残り、新しいクライアントごとに再生イベントの実装が必要になる |
| STTとTTSを同じ方式（OpenAI互換API）へ統一する | STTは交換可能な部品だが、TTSはエンジン固有の設定を持ち、統一の利点が小さい |
| 割り込み判断もフレームワーク（LiveKit Agents等）へ任せる | セルフホストで利用できる判定機能に制約があり、体験の品質を自前で管理できなくなる |

## 影響

- `last_played_audio_sequence`を必須入力とする処理と、全出力確認を待つ`ResponseCompletionPort`の実装を置き換える。
- 推定値と、FEから補正値が届いた場合の値の差を計測できるようにし、d の妥当性を確認する。
- 既存のSTT clientはライブラリ経由の接続へ置き換える。

## 未決事項

- 下り遅延 d の決め方（Session開始時の較正、既存のネットワーク計測からの固定値等）。
- 区間の途中で割り込まれた場合に、区間内のどこまでを再生済みとするか（TTSのタイミング情報、モーラ数による按分等）。
- STTサーバーの選定（speaches等の既製サーバー、または既存`whisper_service/`へのOpenAI互換エンドポイント追加）。
- LiveKit Agentsを採用するか。採用する場合も、ターン判断は手動制御とし、SDKの会話履歴を第二の正本にしない（複数入口ADR §6）。
- TTSのエンジン固有設定を、エンジン側の声のプリセットとして持つか、Cardの`tts_config`に持つか。
