# 音声Session開始準備と失敗後の再試行（2026-09）

## 状態・適用範囲

**ACTIVE**。2026-09-19の#350・#423・#424共通要件整理で採用した判断。
採用は実装・配備・受入済みを意味しない。要求と受入は[共通指示書](../voice-quality-350-423-424-requirements.md)、
定義は[用語集](../glossary.md)、具体的な進捗は各Issueを参照する。

対象は音声会話の開始準備と、準備失敗後のユーザーによる再試行。
[TTS選択ADR](tts-engine-reference-voice-2026-09.md)のSession設定固定、
[Backend集約ADR](voice-backend-authority-2026-09.md)の正式発話・入力認可、
[環境分離ADR](local-dogfood-environment-2026-08.md)の共有サービス所有を維持する。

## 背景

#350の過去測定には、初回応答に先立つモデル読み込みに約41〜56秒を要した例がある。
これは現行構成の再現性・原因を証明しないが、最初の発話後に準備待ちが現れる問題と、
通常応答の速度を切り分ける必要がある。

開始UI、発話受付、下位サービスの失敗、再試行を一貫して扱う必要があるため、
待ち時間上限と再試行の判断を記録する。

## 決定

1. 音声会話の開始操作後は「準備中」を表示し、必要な準備の完了後に発話受付を始める。
2. 準備全体には固定時間上限を設けない。経過時間だけを理由に準備を打ち切らない。
3. 下位処理のタイムアウトとエラーを検出し、準備失敗として扱う。
   要求・queue・worker・入力ACK等の既存期限を一括撤廃する判断ではない。
4. 失敗した処理と理由を表示し、開始準備全体の再試行はユーザー操作で行う。自動再試行しない。
5. 開始操作から発話受付可能までを準備時間として、初回応答・継続応答と分けて記録する。

## 検討した代替案

| 案 | 利点・負担 | 判断 |
|---|---|---|
| 最初の発話後に必要な準備を行う | 開始UIの待ちを減らせる一方、発話後に長い待ちが現れる | 開始時に準備する案を採用 |
| 準備全体に60秒等の上限を設ける | 待機を一定時間で打ち切れるが、正常な長い準備も失敗となる | ユーザー判断により不採用。処理側のtimeout・errorを扱う |
| 準備失敗後に自動でやり直す | 操作を減らせるが、原因が解消しない状態で重い準備を繰り返す | 手動再試行を採用 |

## 影響・既存契約との境界

- 開始操作後の待ちが長くなる場合がある。準備時間を別途残し、TTFA短縮だけで全体が高速化したと主張しない。
- 準備失敗を成功や発話受付可能へ読み替えない。具体的な接続・表示は実行側へ委ねる。
- [移設契約](../voice-backend-migration-contract.md)のBE準備4秒／FE入力ACK待ち5秒は、
  個別の入力認可処理の期限として区別する。Session開始準備全体の上限として流用しない。
- Irodoriの準備・推論・待機等のservice timeoutは引き続き個別に検出する。
  共有サービス内部のworker回復や、既存の通信再接続を手動専用へ変更する決定ではない。
- Session設定固定、取消・旧結果拒否、privacy、既存の停止・終了操作、共有サービス所有を変えない。
- 開始準備と再試行に限って本ADRを優先し、既存ADRの他の境界を置換しない。

## 実装補足：固定人格の入力長計測

モデル事前準備をサポートするProviderでは、モデル準備後に現在のCharacter Cardの固定人格部分を
通常promptと同じ整形・Chat Target・contextで正確に計測する。Ollamaの既存の入力長cacheを使い、
発話後に同じ固定部分を再計測する推論要求を減らす。会話履歴を開く前に行い、
未来の利用者入力、記憶検索・形成、動的なLore選択や回答の先行生成には触れない。

通常応答の本文、入力予算、正確な全体計測は維持する。cacheは本文を保存せずHMACと件数だけを保持し、
通常応答時にもモデルdigest・要求条件・現在の人格本文を照合する。人格編集やモデル変更後に
古い計測値を固定し続けない。未対応Providerには追加の計測要求を送らない。

固定人格の計測はChat Targetの個別timeoutを使い、失敗は推論準備の失敗として表示する。
終了・期限切れは同期workerの推論取消へ伝播し、続く固定部分の計測や履歴作成を開始しない。
これは開始準備全体の時間上限ではなく、発話後のTTFA達成を保証するものでもない。
