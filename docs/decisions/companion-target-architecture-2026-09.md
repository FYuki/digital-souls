# 目標シナリオとモジュール境界の原則（2026-09）

## 状態・適用範囲

**ACTIVE**。2026-09-27〜28のアーキテクチャ見直しで合意した、最終形として目指すユーザーシナリオと構成上の原則。
[複数入口ADR](multi-entry-character-core-2026-09.md)の要件（R1〜R5）へ目標シナリオを追加する。
同ADRの不変条件（人格・記憶・権限の正本は一つ、外部作用はExecution Gateを通す等）は維持する。
会話と会話外活動の分担は[会話・活動エージェントADR](conversation-activity-agents-2026-09.md)、
音声の再生済み範囲とSTT／TTS接続は[再生済み範囲推定ADR](voice-playback-estimation-speech-services-2026-09.md)を参照する。

## 決定時点の前提

- 利用経路はブラウザ（PC・スマホ）のテキスト・音声会話。Desktop（#317）は共通client契約だけがある。
- 共有体験（ゲームやタスクを一緒に行う）を扱う要件・構成は定めていなかった。画面知覚はturn単位の静止画参照だった。
- BackendはFastAPIの単一プロセス。GPUモデル（Whisper、Irodori、Ollama）は共有サービスとして別プロセスに置いていた。
  入口Adapterは同一プロセスに置き、別プロセス向けの認証付きAPIを作らないと決めていた（複数入口ADR §2.1）。
- 推論は用途別TargetでOllama／OpenAI API／Codex runtimeへ割り当てていた。privacy・character-lifeはローカルProviderに限定していた。

## 目標シナリオ

| # | シナリオ | 内容 |
|---|---|---|
| S1 | 利用場所をまたぐ一貫性 | Web（PC・スマホ）とWindowsネイティブクライアントのどこで話しても、同じキャラクターとして応答する |
| S2 | キャラクター設定の一元管理 | システムプロンプト・声・loreをCharacter Cardで一元管理する。各クライアントは設定を持たない |
| S3 | 共有体験 | ユーザーと経験を共有する。ゲームは最初に一緒に見て実況し、後続で一緒にプレイする。タスクをユーザーと分け合う |
| S4 | 複数キャラクター | 複数のキャラクターを扱う。キャラクターごとの記憶・会話の境界を保つ |

## 決定

### 1. 会話状態と活動状態を分ける

ゲームやタスクの進行状況（今どの場面か、誰が何を担当しているか）は、会話履歴とは別の活動状態として持つ。
応答を生成する時点で会話と活動状態を合流させる。活動で起きた出来事は既存の記憶形成を通して経験になる。

### 2. 共有体験の段階

- ゲームは観測と実況から始める。操作（プレイ）は後続とし、操作はExecution Gateと活動ごとの許可を通す。
- 画面・ゲームの観測データは機微情報になり得るため、既存の画面知覚と同じprivacy境界を通す。

### 3. ローカル／クラウドLLMの併用

- 会話の推論はローカルLLMとクラウドLLMを併用する。
- 機微情報の判定はローカルで完結させる。判定より前に、判定対象のデータを外部へ送らない。
- 既存のprivacy・character-lifeのローカルProvider制約は緩和しない。

### 4. モジュール境界と切り出し

- モジュール間は名前空間とAPI（ポート）の単位で疎結合にする。他モジュールの内部実装へ直接依存しない。
- プロセスの分割は事前に決めない。カプセル化を保ち、負荷・障害分離・配置の必要が生じた時点でポートの境界から切り出す。
- GPUモデルは従来どおり共有サービスとして所有し、アプリのプロセスへ読み込まない。

### 5. 外部から呼ばれる入口

- Core側にMCPサーバー等の汎用の受け口は置かない。接続元は自作の入口に限る。
- 外部アプリから呼ばれる必要が生じた時点で検討する。候補はOpenAI互換APIとする。
- Claude Code・Codex等への開発タスクの依頼は、キャラクターから外部への作用として扱う。
  既存の外部MCP接続とExecution Gateを通す（2026-09時点でCodexのMCPサーバー機能は廃止されており、別Adapterが必要）。

## 採らなかった案

| 案 | 採らない理由 |
|---|---|
| 音声・egress（外部送信）等を最初から別プロセスにする | 必要性が測定で示される前に分けると、プロセス間APIと認証の保守が増える。ポート境界を保てば後から切り出せる |
| Core側にMCPサーバーを置き、外部から会話外活動を依頼できるようにする | 現時点の接続元は自作の入口だけで、汎用性を先に作る必要がない |
| キャラクター設定を版付きバンドルとしてセッションごとに固定する | 最新のCardを参照する運用で足りる（会話・活動エージェントADR） |
| 1から作り直し、評価器等だけを移設する | 既存のドメイン層はFastAPI・LiveKitへ依存しておらず、記憶形成・privacy・Execution Gate・テスト資産を捨てる損失が大きい。改修で目標構成へ移行する |

## 影響

- Windowsネイティブクライアント（#317）は、共通client契約に加えて画面・ゲームの継続的な観測と、後続の操作を担う。
- 活動状態の保存先・スキーマと、観測イベントの契約を新たに定める必要がある。

## 未決事項

- 機微度に応じてターンごとにローカル／クラウドLLMを選ぶ方式と、公開範囲（`public`／`private`）との関係。
- Windowsクライアントの観測方式（キャプチャAPI、前処理の配置）と、ゲーム操作の制御ループ。
- 活動状態の保存先・スキーマ。
- 複数キャラクター時のエージェント・推論資源の割り当て。
- 外部から呼ばれる入口を作る場合の認証と、呼出主体（`owner`／`other`）の決め方。
