# #340 Episodic Memory 実行指示書（2026-09-13）

## 目的と状態

日常の経験をEpisodeと関連Factとして形成・管理し、後の通常会話で利用できるようにする。
本書は#340の既存契約と2026-09-13の対話で合意した要件を実行側へ渡す指示書である。
設計・要件の確定を表し、アプリケーション実装・実LLM受入の完了は表さない。

Epicブランチは `epic/340-episodic-memory`。
#352で反映した[境界ADR](decisions/episode-fact-semantic-boundaries-2026-09.md)を基礎とし、
今回の日常経験・経験単位・Fact更新・管理操作・dev受入の追記を適用する。
用語は[記憶・人格の用語契約](decisions/memory-personality-terminology-2026-09.md)を参照する。
進捗・完了状態の正本はGitHub Issueとする。

## 合意した対象範囲

- 日常経験も保存対象に含める。特別な重要性がないことだけでは除外しない。
- 同一スレッドの一続きの経験は複数発言・非同期抽出をまたいでもまとめる。
- 改めて語り直した経験は新規Episodeとし、話題の対象への明確な補足・訂正は既存Factの更新とする。
- 明示的な仮定・創作を話した経験も、その文脈をEpisode / Factから検索・会話利用まで保持する。
- 同一スレッドの明確な会話中の訂正を自動反映し、管理UIからもFact単位で訂正・削除できるようにする。
- dev環境で抽出・保存・管理に加え、通常会話での検索・利用まで実接続で受け入れる。

「既存Episodeへの追加」を話題のFactの内容更新と混同しない。
Fact Updateは対象が明確な安定IDの内容版更新、Fact Mergeは別Fact間の同一性を版付きID関係で表す処理である。
内容が変わらない再言及では、Fact本文の更新は不要で、今回の取得元の参照を残す。

## 維持する制約と対象外

- 所有characterと行為者・実参加者・話題の人物、経験日時とFactの対象日時を分ける。
- 内容上の必須はWhatの述語のみ。管理ID・出典/版・状態等は別途必須。欠損の推測補完やWhyの推論をしない。
- 日時はconfig timezoneと元発言日時を基準に解釈し、日/月等の精度・使用timezoneを保持する。
- 別Factの自動統合は同一character・同一threadの5W一致と文脈を確認できた場合だけ。unknown同士、日時包含、同名、別回の可能性は一致の根拠にしない。
- 明確な補足・訂正の対象特定と、別Fact間の自動統合を分ける。前者に変更前後の5W一致を要求せず、対象不明なら既存Factを上書きしない。
- source / Fact / 参照 / 統合関係の版検証と即時失効、循環・別character参照禁止、再試行・並行処理の冪等性を維持する。
- privacy、保存拒否、画面由来情報の長期記憶除外、SQLite正本 / Chroma派生index / outboxを維持する。拒否本文を記録しない。
- #354の別thread Fact統合、#48の整理再実装、#341のSemantic形成、#100の一般化/Reflection、#101/#102/#249の実装は対象外。
- 新しい候補ごとの手動承認・手動Fact統合フローを追加しない。
- #289の未リリース形式の互換・移行は要求しないが、mainからの安全なschema適用と既存データ保護は必要。

## 重要な観測可能な振る舞い

以下は今回の追加要件の受入シナリオである。
既存の欠損・日時精度・同一性の見送り・privacy・競合・回復等の受入も#344と境界ADRに従って維持する。

```gherkin
Feature: 経験とFactを分けた形成と利用

  Scenario: 日常の一続きの経験を複数の抽出実行で分断しない
    Given 保存条件を満たす同一スレッドの会話がある
    When 「今日うどんを食べた」「駅前の店で」「おいしかった」と一続きに話し
    And その途中と後で非同期抽出が実行される
    Then 特別な重要性がないことだけでは保存を拒否しない
    And 一続きの「昼食の話を聞いた経験」は1 Episodeにまとまる
    And 各情報の元発言・版・抽出範囲を追跡できる

  Scenario: 語り直した経験を追加して同じ対象のFactを更新する
    Given 旅行の話を聞いたEpisodeとFactが保存されている
    When 同じスレッドで後日その旅行を改めて語り直し
    And 対象Factを明確に特定できる場所の補足を得る
    Then 新しい「聞いた経験」のEpisodeを追加する
    And 既存Factの安定IDを保って内容版と補足の出典を更新する
    And 新EpisodeからそのFactと今回の取得元を追跡できる
    And 元Episodeの経験日時と元出典を失わない

  Scenario: 内容が変わらない語り直しではFact本文を変更しない
    Given 保存済みFactへの再言及対象が明確である
    When 後日同じ出来事を新しい情報なしに改めて語り直す
    Then 新しいEpisodeと今回の取得元の参照を残す
    And Fact本文を再言及だけの理由で変更しない

  Scenario: 明確な会話中の訂正を自動反映する
    Given 同一スレッドの「昨日うどんを食べた」由来のFactがある
    When その発言を明確に指して「ごめん、そばだった」と訂正する
    Then 変更前後の5W一致を要求せず対象Factを更新する
    And 元発言と訂正の出典・版を追跡できる
    And 旧版に依存する関係を停止して再評価する
    And 古いsnapshotの再処理で訂正前の内容を復活させない

  Scenario: 対象が曖昧な補足で既存Factを上書きしない
    Given 同一スレッドに別々の旅行Factがある
    When どの旅行への補足か特定できない場所の発言を得る
    Then 意味類似や日時の重なりだけで既存Factを更新しない
    And 保存条件を満たす追加情報は曖昧さを保って保持する

  Scenario: 仮定や創作の文脈を保存と利用で維持する
    Given 保存条件を満たす「もし二人で月へ旅行したら」という会話がある
    When 非同期抽出して保存し後の通常会話で検索・利用する
    Then 月旅行を想像して話した経験として扱う
    And 関連Factにも仮定・創作内の情報である文脈が残る
    And 実際に月へ旅行した経験として答えない

  Scenario: 管理画面でFactを訂正する
    Given Episodeから参照される保存済みFactがある
    When 管理画面から対象Factの5Wや内容を訂正する
    Then 元会話を書き換えずに共通保存契約を通して更新される
    And 訂正の版・出典と参照・統合関係の有効性を確認できる
    And 後の検索・通常会話で訂正後の有効な内容を利用する

  Scenario: 管理画面で削除したFactを会話で復活させない
    Given Episode・統合関係・検索indexから参照されるFactがある
    When 管理画面でそのFactを削除する
    Then 依存する内容と関係を既存の削除・失効契約に従って利用停止する
    And 古いindex・別参照・再抽出から削除内容を復活させない
    And 後の通常会話で削除内容を記憶として利用しない
    And 別の「聞いた経験」を無条件に物理削除しない
```

## dev環境での最終受入

[テスト方針](testing-policy.md)に従い、dev環境内に通常データから分離したテストdata rootを用意する。
実Backend・実LLM・実SQLite・実Chroma/Embeddingとブラウザの通常会話・管理UIを通す。
共有推論サービスを使用する場合はプロセスを所有・停止せず、dogfoodのアプリ・DB・会話データを試験対象にしない。

通常会話から合成シナリオを入力し、抽出・保存後に記憶を必要とする会話で利用を確認する。
直近履歴だけで正答できる条件を避け、参照ID・版等を既存metadata-only policy内で追跡し、
検索された有効な記憶に基づく応答であることを示す。
別スレッドを使って履歴の影響を除く場合も、保存済み記憶の検索と#354の別thread Fact統合を混同しない。

実行commit、model・prompt・policy・config、環境区分、scenario、期待値、結果、失敗・未検証事項を記録する。
通常ログへ秘密・生本文・prompt・raw出力を保存しない。
mock/fixture/readinessや候補のDB直接投入だけを実接続合格にせず、未達のシナリオを除外して完了扱いにしない。
