# #341 意味記憶の実行指示書

## 状態と目的

2026-09-14の仕様整理で合意した要件。採用設計であり、実装・性能評価・実接続受入の完了宣言ではない。
キャラクターが汎用的な知識・事実を会話から取得し、別スレッドの会話でも根拠と状態に従って利用できるようにする。

## 概念・責務

- Episodeは記憶所有者本人の経験。ユーザーから話を聞いた経験を含む。
- Factは経験内の事実・申告内容。外部世界で検証済みの真実を意味しない。
- Semantic Memoryは特定の経験を離れて使える汎用的な知識・事実。変化する居住地・好みも含む。
- #341は共通正本、DIRECT_EXTRACTION、訂正・時間変化・矛盾、検索、管理UIを所有する。
- #100はEXPERIENCE_DERIVEDの一般化・根拠評価とReflectionを所有する。共通保存入口・根拠失効時の再評価契約を#341が提供する。
- スレッドは会話履歴を抽出する枠であり、意味記憶の所有・照合・更新・検索の境界ではない。所有境界はcharacter_id。
- 外部活動からの学習は別Epic。外部文書・情報源の接続は初回に含めない。

## 取得・共通保存

保存済み会話のユーザー明示発言から非同期に候補を抽出する。生成されたassistant発言は単独の根拠にしない。
「そうだよ」などは直前文脈で対象を解釈できるが、根拠はユーザーの確認発言に置く。
通常は前回正常に処理を完了した位置以降を抽出の起点とし、必要な過去文脈と既存知識を参照する。
過去出典の編集・削除は別の失効・再評価経路で扱う。失敗・再起動時も未処理分を失わず、同一出典・版の再試行で増殖させない。

共通正本はSQLite、Chromaは派生index。少なくともcharacter、内容／命題、形成経路、各根拠のIDと版、
confidence／evidence、適用時期、状態、訂正・置換関係、作成・更新日時を保持する。
Candidateと検証済み正本を分け、schema・source・character・privacyをコード側でも検証する。
形成方法と情報源を混同しない。Fact統合や同じ情報の再表現を独立根拠の増加として扱わない。

## 訂正・矛盾・管理

明示訂正でなければ原則として時間変化とし、旧情報を過去の状態として保持する。
変化時期は明示情報から解釈し、不明なら推測で補わない。
通常は変化しない属性の食い違いは矛盾保留とし、どちらかを確定知識として断定しない。
自己申告と経験からの一般化の食い違いだけでは一般化を停止せず、会話では自己申告を優先する。
これはsource自体の失効とは別であり、無効なsourceを根拠にした利用は継続しない。

UIは内容、形成経路、出典と版、根拠Episode、confidence、適用時期、状態、訂正・無効化履歴を監査できる。
本文訂正はユーザーの自己申告由来だけに許可し、APIでも制約する。元の発言を書き換えずUI訂正として追跡する。
削除は形成経路を問わず可能。元会話・Episodeは同じ操作では削除しない。
削除本文を履歴から復活させず、同じ出典・版による再生成を防ぐ。新たな発言・経験からの候補取得は許可する。

保留矛盾は後続の内省から参照可能にする。キャラクターの興味に沿う質問への表出は許容するが必須ではなく、
内省からの質問生成・実行、および「私からはそう見える」という主観の表出は今回のMVP外。

## 推論・負荷・モデル選定

既存Inference Target／Provider境界を使い、意味記憶用LLMを会話用から独立して設定できるようにする。
対応Provider内のモデル変更で保存形式・業務ロジックを変更しない。未知Providerへの新規Adapter追加は別の実装判断となる。
入力・出力上限、timeout、同時実行数、モデル固有optionsを設定可能にし、暗黙fallbackやprivacy緩和を追加しない。
通常会話を優先する。高負荷時は抽出開始・反映の遅延を許容し、未処理分を保持して後から処理する。品質基準は下げない。
2026-09-15の追加合意として、会話開始時は実行中の記憶抽出を中断し、会話が落ち着いた後に再試行する。
対象はEpisode・意味記憶の抽出と、その処理内の推論。元会話と未処理予約は保持し、保存済み分は重複させない。
中断前に完了した原子的な保存は維持する。未完了の生成結果を保存・処理済みにしない。

開発用Gemma 4はe4bと12bを比較して選ぶ。汎用的な多モデル比較を今回の完了条件へ拡張しない。
同じ固定case・期待値・共通promptを使い、本番呼び出し経路でcache無効の各3回を測定する。
各回・各分類90%以上、固定case内の禁止情報保存・別character混入0件を必須とする。
抽出判断、命題・主体・出典、文脈確認、同一性、明示訂正、時間変化、固定属性矛盾、自己申告優先を分類別に評価する。
評価caseと期待値はprompt調整前にcommitで固定する。enum等の判定は決定論的に採点し、
自由文で独立judgeを使う場合も採点基準・judgeを被評価モデルから独立して固定する。
モデル別prompt調整を行った比較は、共通prompt比較と区別し版を記録する。
モデルID／digest、量子化、thinking等の設定、prompt／policy／schemaの版、commit、入力長、
誤判定内訳、処理時間、tokens、メモリ使用量、会話への影響を記録する。
品質が同程度ならe4b、重要判断の改善があり実行負荷も許容できるなら12bを選ぶ。
両モデルとも未達なら採用確定・Epic完了にはしない。

## 観測可能な受け入れ条件

```gherkin
Feature: 会話からの意味記憶の取得と利用
  Scenario: 単一発言からの取得と別スレッドでの想起
    Given ユーザーが「誕生日は5月10日」と一度述べた
    When 増分抽出が検証済みの知識として保存する
    Then DIRECT_EXTRACTIONとして元のユーザー発言IDと版を保持する
    And 同一キャラクターの別スレッドの会話で検索して利用できる

  Scenario: 出来事と推測を知識に読み替えない
    Given ユーザーが「昨日紅茶を飲んだ」とだけ述べた
    When 意味記憶候補を抽出する
    Then 「紅茶好き」を直接取得した知識として採用しない

  Scenario: キャラクターの自己生成だけを根拠にしない
    Given assistantだけが「あなたの誕生日は5月10日」と述べた
    When 後続にユーザーの確認がない
    Then その主張を意味記憶の根拠として採用しない

  Scenario: 明示確認を文脈から解釈する
    Given assistantがユーザーの好みを質問した
    When ユーザーが「そうだよ」と明示確認する
    Then 対象を文脈から特定し確認したユーザー発言を根拠にできる

  Scenario: 変化と誤り訂正の区別
    Given 「大阪に住んでいる」という知識がある
    When ユーザーが「東京に引っ越した」と述べる
    Then 大阪は過去の状態として保持し現在は東京を優先する
    And 不明な引越日を補わない

  Scenario: 明示訂正
    Given 「誕生日は5月10日」という知識がある
    When ユーザーが「言い間違いで5月11日」と訂正する
    Then 旧知識を訂正で置き換え旧内容を現在の知識として使わない

  Scenario: 固定属性の矛盾保留
    Given 「誕生日は5月10日」という知識がある
    When 訂正の明示なしに「誕生日は5月11日」と述べる
    Then 食い違いと両方の根拠を保持し日付を確定して断定しない

  Scenario: 一般化と自己申告の共存
    Given 経験から「コーヒー好き」と一般化されている
    When ユーザーが「コーヒーは好きではない」と述べる
    Then 一般化を食い違いだけでは停止しない
    And 会話では現在の自己申告を優先する

  Scenario: 出典失効と古いindex
    Given 検索indexに古い知識が残っている
    When 根拠発言または根拠Episodeが編集または削除される
    Then SQLiteと根拠の有効性で直ちに古い知識を利用対象外にする
    And EXPERIENCE_DERIVEDは後続の再評価へ渡せる

  Scenario: UI訂正の権限
    Given 自己申告由来と経験からの一般化の知識がある
    When UIまたは直接APIから本文を訂正する
    Then 自己申告由来だけを訂正できる
    And UI訂正の根拠と履歴を追跡できる

  Scenario: 削除と再処理
    Given ユーザーが意味記憶をUIから削除した
    When 同じ出典と版を再処理する
    Then 削除した知識を復活させない
    And 元会話とEpisodeはその操作で削除しない
    And 新しいユーザー発言を根拠にする取得は可能である

  Scenario: 会話優先と回復
    Given 意味記憶の未処理会話がある
    When 会話処理の負荷が高い
    Then 抽出の開始を待機でき未処理分を失わない
    And 再起動または失敗後の再試行でも二重保存しない
```

## 実接続受入と保護境界

選定したモデルを用い、dev/test専用data rootと合成会話で通常会話→抽出→実SQLite→実Chroma／Embedding→
別スレッド検索→応答への利用→UI訂正／削除→後続応答への反映を確認する。
履歴だけで答えられる条件、mock、readiness、DB直接投入を実LLMからの受入の代用にしない。
#100からの共通保存・検索・根拠失効は契約試験で確認し、#100の一般化ロジック完成を要求しない。
実接続・promptfoo・unit/module・browserの証跡を分け、実行commit・環境・モデル・期待値・結果・未検証事項を残す。
既存main／dogfoodの会話、設定、model、backup、secretを保護する。DB全体の初期化をしない。
共有推論サービスはテストが所有・停止しない。

## 実装側へ委ねる事項

合意した観測可能な振る舞いを維持する範囲で、物理schema、処理分割、用途別Target名、batch分割・再試行間隔、
索引・照合候補の取り方、API形状、UI配置、固定caseの具体的な文面を既存契約に沿って決める。
新たな要件変更を委任事項に混ぜない。
